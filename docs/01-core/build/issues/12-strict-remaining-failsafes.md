## Requirements & constraints

**Failsafe posture — PRD §11**
- **Default: graceful + warn.** `build` exits non-zero **only on hard failures** (read-only output, explicit-port-and-taken in `dev`).
- **`--strict`** (both flag + config entry) **promotes all warnings to failures** — escalated by strict: collision `.md`/`.mdx`, broken links (07), broken imports (05), malformed frontmatter (04), two-asset conflicts, plus everything else warning-level.
- Every error-prone path has a **deterministic rule-based resolution + informative CLI feedback** describing the resolution (§11).

**Resolutions owned here**
- **Same-route `.md` + `.mdx`**: `.md` wins; feedback records the resolution.
- **Read-only output**: hard failure, non-zero exit (already thrown by `publishSite` per CONVENTIONS.md).
- **Symlinks in the tree**: all skipped in v1 (internal + external), **each logged** — the skip already landed in the ticket-01 content-graph engine; ticket 12 must add the *logging* and its strict escalation.
- **Two source assets → same output path**: logged rule-based resolution + warnings.
- **Dev port conflict**: implicit-default increments + warns (08); explicit-config fails (hard).
- **Output dir conflict**: written like a normal build tool (write + remove prior files), no prompt — already in `publishSite`.
- **Empty root / no renderable files**: warning + empty nav/message page; exit 0 (landed in 01).

**Boundaries**
- Warnings from 04/05/07/09 (malformed frontmatter, broken imports, broken links/media, broken config) are **generated by those tickets** into a shared collection this ticket clearly escalates; 12 must not re-tag their rules.
- `--strict` is an option on both flag and config surfaces (ticket 09) — precedence flag > config > default.

## Open decisions

1. **Warning aggregation contract.** A shared typed warning record (kind + message + source path) collected during build/render, printed once per build, escalated by `--strict` to failures — define the record shape + collection module now (04/05/07/08/09 all emit into it). Exit code for strict-failure: distinguish from hard failures.
2. **Escalation model.** Does `--strict` force the **same exit code** as hard failures (recommended: non-zero, e.g. 1) and include a stable message? What counts as the "hard" set unaffected by strict (`--strict` does not rescue read-only) — document the matrix per §11.
3. **Collision determinism & scope.** `.md`-wins is deterministic; decide whether the resolution emits a **favored** entry only, or renders both where one is the chosen route and the conflict stays listed. Requires a defined order over the graph (already sorted). Also whether the warning text must include both source paths.
4. **Symlink logging shape.** Content engine skips symlinks now (no log). Add per-symlink warning (path) — deterministic ordering of log lines (byte order). Decide whether a *directory* symlink result is skipped silently or logged once per dir.
5. **Config-strict precedence.** `--strict` as config entry: whether config can disable strict set by flag (flag > config per 09). No hard edge, but consistent with precedence.
6. **Asset-conflict with 07 vs 12.** Two sources mapping to the same output — ownership crosses 07 (copy) / 12 (report). Decide which side owns & tracks the conflict so strict applies to both the build and asset stages.
